## 1. URGENT, UNRESOLVED: the API key restriction may have broken Moon AI in production

**What happened.** On 23 Aug the iOS key (`61d1519e-7fec-40cc-99e0-88e96c026517`) was
restricted in Google Cloud to Application restrictions = iOS apps, bundle
`com.niyora.app`. It looked like a clean security win, and `check-appcheck.mjs`
flipped from ALLOWED to BLOCKED, which is what we wanted from a laptop.

**Then the dev build stopped working.** Every AI call now returns:

```
403  API_KEY_IOS_APP_BLOCKED
     iosBundleId: "<empty>"
```

**The likely cause.** `@react-native-firebase/ai` appears to make its request from
JavaScript, not native code. A JS `fetch` does not carry the
`X-Ios-Bundle-Identifier` header that Google's iOS key restriction checks, so the
header arrives empty and the key is rejected. If that is right, the restriction
blocks the app itself, not just outsiders, and it would block the **App Store
build too**, since the restriction is server side and applies to every caller.

**Not yet confirmed.** The 403s were observed while the model and location were
temporarily pointed at `gemini-3.7-flash` / `global` for an availability probe.
That probe has been reverted (`us-central1`, `gemini-2.5-pro`), but nobody has
re-run a moment on the reverted config to confirm the 403 persists.

**Do this first:**

1. Open the app on the phone, run one moment, watch the Metro log for `[moon-ai]`.
2. If the 403 is still there on the shipping config, remove the Application
   restriction on that key (set it back to None) in Google Cloud, and confirm the
   flow recovers.
3. If it recovers, the restriction is unusable with this SDK. Say so in the
   launch checklist and rely on App Check enforcement instead, which is the real
   protection anyway.

**This also explains something we could not read.** The App Check panel showed 0
verified and 0 unverified requests for 7 days. If live users started getting 403s
on the 23rd, that is consistent.

## 4. What shipped

**PR #324** (merged, 7 commits)

- Model `gemini-2.5-flash` to `gemini-2.5-pro`, thinking budget 512. Measured:
  reads that hand her own words back 39% to 15%, repeats 9% to 1%, blank cards
  3 to 0.
- Found the cause of the blank cards: `maxOutputTokens` counts thinking tokens
  and the cap was 256, so any thinking budget was spent before a word of the
  reply. The two are now tied together.
- Per-slot thinking: `has_event` and `feelings` get 128. 8/8 correct at both 128
  and 512, but 512 spent five times the tokens. **Never set 0 on a pro model**,
  it returns an empty body and would silently disable the whole flow. Test guards it.
- `responseSchema` on all JSON slots plus the crisis classifier.
- Time-aware routing (acute / long-standing / recent).
- Three cards became interactions: **scale** (she places her absolute on 0 to
  100), **responsibility** (she supplies the hands, her share is the remainder),
  **load** (she lists what is on her and sorts it).
- Reactions persist across sessions, encrypted, and feed forward as a lean.
- A delete that actually exists, with a test that fails the build if a new
  storage key is in neither the content nor settings list.
- Badges name the act, not the wound. A test blocks conquest language on grief.
- Prefetch of the next card, and the de-duplication bug that was making it slower.
- Colour tokens applied, 44 hand-picked white alphas to zero.

**PR #325** (merged, 2 commits)

- **Signal** rebuilt. It had failed three prompt rewrites across three models.
  The app already asks her the feeling one beat earlier, so `SIGNAL_POINTS`
  (authored, per constellation) now hands the model the canonical referents and
  it grounds them in her situation. Recognition instead of generation.
- **Load read-back**: once she has listed and sorted, the model reads her own
  list back structurally. "Almost everything on this list comes back to the flat
  and this one landlord."

## 5. The principle worth keeping

Every card that failed, failed the same way, and the fix was always the same shape:

> The model is good at operating on what she gives it, and bad at inventing what
> she has not.

Load, responsibility and signal all broke because they asked the model to know
something only she knows. Each works now because she supplies the material and
the model works on it. Reach for this before writing another prompt rewrite.

## 6. The harness

```bash
node --experimental-strip-types scripts/scenario-test.mjs --thinking 512 --out run.json --tag mine
python3 scripts/results-to-xlsx.py before.json run.json -o out.xlsx
```

- Runs the REAL prompts on 13 scenarios, three pulls deep.
- **Free.** Uses the Gemini Developer API when `GEMINI_API_KEY` is set (it is, in
  `.env.local`). Defaults to flash. Pass `--model gemini-2.5-pro` only for a final
  check. Prints what each run cost.
- **Two runs of identical prompts differ by up to 5 points.** Anything smaller is
  noise. Do not claim it.
- Recorded in the prompts as DO NOT ADD blocks, with numbers: worked examples
  made reads worse (8.6% to 15.4%), and an in-call "generate five then discard"
  pass discarded nothing.
- The harness still calls the old slots for `middle` and `whose_weight`, which are
  interactions now, so exclude those cards when scoring.

## 9. Working style that mattered

- Short replies. Neha has ADHD; long text costs real effort. Lead with the
  concrete thing, show a worked example rather than an explanation.
- No em dashes anywhere, including prompt strings. The model copies the
  punctuation it is fed.
- Measure before claiming. Several confident-sounding conclusions this session
  turned out to be noise, or the metric penalising the shape that works.
